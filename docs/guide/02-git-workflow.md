# 仓库与分支、提交与 PR

> 我们怎么改代码：分支命名、提交信息、PR 与评审的最低要求。
> 预计阅读：6 分钟

## 1. 分支

- `main` 是**保护分支**，不直接推，所有改动走 PR。
- 功能分支从 `main` 切出，命名 `feat/<简短描述>`：

```bash
git checkout main && git pull
git checkout -b feat/demand-labels
```

| 前缀 | 用途 |
|---|---|
| `feat/` | 新功能 |
| `fix/` | 修 bug |
| `docs/` | 只改文档 |
| `chore/` | 构建、依赖、杂项 |

## 2. 提交信息

一行说明白「改了什么」，不要写「update」「fix bug」。需要时正文补原因。

```
feat(demands): 需求支持标签与难度
fix(projects): 邀请成员时重复点击报 409
docs(guide): 补充 SSH 拉代码说明
```

- 一个提交只做一件事；无关改动拆开。
- 提交前先 `git pull --rebase origin main`，避免无意义的 merge 提交。

## 3. 自测清单（提 PR 前）

- [ ] 本地能起、页面能走通主流程
- [ ] `npm run typecheck`（或 `tsc --noEmit`）通过
- [ ] 没有把 `.env`、密钥、真实用户数据提交进去
- [ ] 数据库变更写了迁移（不要手改线上表结构）

## 4. PR

- 标题与提交信息同样式；描述写清楚：改了什么、怎么验证、有什么风险。
- 至少一位成员 review 通过再合并；作者自己不能直接合自己的 PR。
- 合并前确保 CI/自测通过；合并后删掉功能分支。

## 5. 评审看什么

1. 有没有安全问题：鉴权、越权、密钥泄漏、SQL 注入。
2. 有没有破坏兼容：接口字段、数据库迁移顺序。
3. 边界条件：空列表、重复提交、并发、权限不足。
4. 可维护性：命名、重复代码、过度设计。

评审意见就事论事；被指出问题不用防御，改完回复一句即可。
