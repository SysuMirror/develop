# 需求流程

> 一条需求从发布到验收的生命周期，以及发布时该写清楚什么。
> 预计阅读：5 分钟

## 1. 状态机

```
待接单 waiting ──接单──> 进行中 accepted ──提交──> 待确认 review ──验收──> 已完成 completed
      │                      │                        │
      └──────────── 挂起 suspended <────恢复────────────┘
```

| 状态 | 谁能操作 | 下一步 |
|---|---|---|
| 待接单 | 任何登录的开发者可接单 | 接单人开始做 |
| 进行中 | 接单人提交完成 | 进入待确认 |
| 待确认 | 发布者或项目所有者/管理员验收 | 通过则已完成，驳回退回进行中 |
| 挂起 | 发布者或项目所有者/管理员 | 恢复后回到挂起前的状态 |
| 已完成 | 只读 | 可作为后续需求的参考 |

## 2. 发布一条需求

发布入口在项目详情页（只有项目成员能发布）。发布前确认：

- **标题**：动词开头，一句话说清结果，例如「需求列表支持按标签筛选」。
- **细节**：背景、期望效果、涉及范围。
- **验收标准**：写成可勾选的清单，提交与验收都对着它。
- **标签**：前端 / 后端 / 数据 / 文档 / 测试，方便别人筛选。
- **难度**：`新手任务` 请标 starter，给刚进组的人练手。
- **预计工时**：按小时估，估不准写区间取上限。
- **期望完成时间**：留空表示不限期，别把日期当摆设。

## 3. 接单前先看三件事

1. 验收标准是否明确；模糊就先在需求下问清楚再动手。
2. 自己是否有时间在期望时间内交付。
3. 是否需要项目权限（代码仓库、数据库、部署环境），需要就提前说。

接单后建议在需求里留一句「计划怎么改」，避免方向跑偏。

## 4. 提交与验收

- 交付时附：改了什么、怎么验证、截图或链接。
- 验收人对照验收标准逐条过；不通过要写清原因，不要只说「不行」。
- 验收通过后需求锁定，不再改正文；有后续工作另开一条需求。

## 5. 一条好需求的样子

```
标题：需求列表支持按标签筛选
细节：列表页顶部加一个标签输入框，输入即过滤；与状态、范围筛选可叠加。
验收：
- [ ] 输入标签后列表只剩含该标签的需求
- [ ] 与状态筛选叠加时结果正确
- [ ] 刷新后筛选条件保留
标签：前端      难度：新手任务      预计：4 小时
```
